================================================================================
SECTION 4: WEB3 INTEGRATION & WALLET CONNECTION
================================================================================

Q16. How does wallet connection work in your application?
ANSWER: Using MetaMask and ethers.js:
- Detect if MetaMask is installed (window.ethereum)
- Request account access via eth_requestAccounts
- Create BrowserProvider from window.ethereum
- Get signer for transaction signing
- Listen for account and network changes
- Auto-reconnect on page reload if previously connected

CODE REFERENCE: contexts/Web3Context.tsx

Q17. What is the purpose of the Web3Context?
ANSWER: Provides global state management for Web3 connection:
- Stores account address, chainId, connection status
- Exposes connect/disconnect functions to all components
- Handles network switching
- Manages loading states
- Listens for wallet events (account/network changes)
- Prevents prop drilling by using React Context

Q18. How do you ensure users are on the correct blockchain network?
ANSWER:
- Check chainId after connection
- Compare with DEFAULT_CHAIN.chainId (Polygon)
- If wrong network, call switchNetwork()
- Use wallet_switchEthereumChain RPC method
- If network not added, use wallet_addEthereumChain
- Reload page after network change to reset state

Q19. Explain how transactions are signed and sent.
ANSWER:
1. Get signer from connected wallet
2. Create contract instance with signer
3. Call contract function (e.g., registerTrademark)
4. MetaMask prompts user to review and sign
5. Transaction sent to blockchain
6. Wait for confirmation (tx.wait())
7. Extract data from transaction receipt
8. Update UI and database

CODE REFERENCE: utils/contracts.ts

Q20. What error handling do you implement for Web3 operations?
ANSWER:
- Check MetaMask installation before operations
- Handle user rejection (error code 4001)
- Network mismatch detection and switching
- Transaction failure handling
- Gas estimation errors
- Timeout handling for slow transactions
- User-friendly error messages

Q23. How does the registration flow work from UI to blockchain?
ANSWER:
1. User fills form on /register page
2. Files uploaded to IPFS via API route
3. Metadata JSON created and uploaded to IPFS
4. Connect wallet and get signer
5. Call registerTrademark() on smart contract
6. User signs transaction in MetaMask
7. Wait for blockchain confirmation
8. Extract tokenId from event
9. Store metadata in Firebase
10. Redirect to trademark detail page

CODE REFERENCE: pages/register.tsx, pages/api/upload/ipfs.ts

- Backup for IPFS data

Q26. How does trademark verification work?
ANSWER:
1. User registers trademark (status: pending)
2. Admin reviews submission in admin dashboard
3. Admin can verify or reject with reason
4. Verification updates both Firebase and blockchain
5. Only verified trademarks appear in marketplace
6. Verification badge displayed on trademark cards
7. Admin action logged for audit trail

CODE REFERENCE: pages/api/admin/verify-trademark.ts

Q27. Explain the marketplace listing process.
ANSWER:
1. Owner navigates to their trademark
2. Clicks "Create Listing" button
3. Chooses sale or license type
4. Sets price in ETH
5. For licenses, sets duration (or perpetual)
6. Optional: Set listing expiration
7. Transaction sent to marketplace contract
8. Listing stored on-chain and in Firebase
9. Appears in marketplace for buyers

Q28. How do you handle product verification?
ANSWER:
- Buyers can verify products using registration number
- System checks blockchain for matching trademark
- Displays owner information and verification status
- Shows IPFS-stored trademark images
- Confirms authenticity via immutable blockchain record
- Prevents counterfeit products

CODE REFERENCE: pages/verify.tsx, components/ProductVerification.tsx

Q29. What is the rating system and how does it work?
ANSWER:
- Buyers can rate creators after purchase/license
- 1-5 star rating with optional review text
- Stored in Firebase with reviewer address
- Average rating calculated and displayed
- Helps build trust and reputation
- Prevents spam by requiring wallet connection
- Ratings visible on creator profiles

CODE REFERENCE: pages/api/ratings/create.ts, components/RatingModal.tsx

Q30. Explain the admin dashboard functionality.
ANSWER: Admin can:
- View pending trademark verifications
- Approve or reject trademarks with reasons
- View and resolve user reports
- Suspend malicious users
- Suspend fraudulent listings
- View platform statistics
- Access audit logs of all admin actions
- Monitor system health

CODE REFERENCE: pages/admin/index.tsx

Q31. How does the reporting system work?
ANSWER:
- Users can report trademarks, listings, or users
- Report types: spam, fraud, copyright, inappropriate, other
- Requires reason and optional description
- Stored in Firebase with reporter address
- Admin reviews in dashboard
- Can resolve or dismiss with notes
- Actions logged for transparency

CODE REFERENCE: components/ReportModal.tsx, pages/api/reports/create.ts

Q32. What is the notification system?
ANSWER:
- Real-time notifications for important events
- Types: ratings, sales, licenses, verifications, reports
- Stored in Firebase per user address
- Mark as read functionality

- Helps users stay informed
- Improves user engagement

SECTION 7: SECURITY & BEST PRACTICES
================================================================================

Q33. What security measures are implemented in your application?
ANSWER:
SMART CONTRACT LEVEL:
- ReentrancyGuard for payment functions
- Access control (onlyOwner, ownership checks)
- Input validation
- Safe math operations (Solidity 0.8+)

APPLICATION LEVEL:
- Wallet signature verification
- API route authentication
- Input sanitization
- CORS configuration
- Environment variable protection
- Rate limiting considerations

Q34. How do you prevent common Web3 vulnerabilities?
ANSWER:
- Reentrancy: nonReentrant modifier
- Integer overflow: Solidity 0.8+ built-in checks
- Front-running: Acceptable for marketplace (public prices)
- Access control: Proper ownership checks
- Gas limit issues: Optimized loops and storage
- Phishing: Verify contract addresses in UI

Q35. What happens if IPFS gateway is down?
ANSWER:
- Multiple gateway URLs configured
- Automatic fallback to next gateway
- Timeout handling (10 seconds)
- Try all gateways before failing
- Error message to user if all fail
- Data still exists on IPFS network

CODE REFERENCE: utils/ipfs.ts - fetchFromIPFS()

Q36. How do you handle failed transactions?
ANSWER:
- Try-catch blocks around all blockchain calls
- Parse error messages from MetaMask
- User-friendly error display
- Transaction status tracking
- Retry mechanism for network issues
- Revert reasons shown to user
- No state changes until confirmation
